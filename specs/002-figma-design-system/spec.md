## 1. شرح مبسط لياسر

نبني مرجعًا بصريًا مشتركًا في Figma وقاعدة موافقة تمنع بدء تخطيط أو برمجة أي واجهة قبل أن ترى شكلها وحالاتها وتوافق على Revision محدد منها.

HDL-02 لا تصمم صفحات المشروع كلها. مخرجها المحدود هو **حوكمة نظام التصميم، Foundations قابلة لإعادة الاستخدام، ومجموعة ممثلة من عائلات المكونات** تثبت طريقة التسمية والحالات والربط بإعدادات سلة. تصمم المواصفات اللاحقة صفحاتها وتدفقاتها وPresets الخاصة بها باستخدام هذا الأساس.

هذه المواصفة تحدد ماذا يجب أن يوجد ولماذا وكيف نقبل المخرج. لا تختار ملفات التنفيذ أو تقنية الكود؛ يبدأ `plan.md` فقط بعد اكتمال بوابة Figma وموافقة المالك.

## Clarifications

### Session 2026-08-08

- **أسئلة المالك المطلوبة: 0.** حُسمت النقاط التالية من الدستور و`ROADMAP.md` و`PRODUCT-BLUEPRINT.md` و`FIGMA-WORKFLOW.md` وتقرير HDL-01 المقبول، من دون افتراض قرار منتج جديد.
- HDL-02 تؤسس الحوكمة وFoundations وعائلات مكونات ممثلة؛ تصميم Home وProduct وCollection وSearch وCart والصفحات المساندة والـPresets كاملة مؤجل إلى المواصفات المالكة لها.
- الاعتماد مرتبط بـRevision محدد وسجل Node IDs؛ أي تغيير مرئي أو سلوكي أو في إعداد تاجر بعد الاعتماد يعيد الحالة إلى المراجعة ويتطلب موافقة جديدة.
- أي Variant قابل للاختيار يجب أن يثبت مصدر تحكم مؤكد في الثيم/سلة، وإلا يحمل علامة `Spike` ولا يقدم كخيار قابل للتنفيذ.
- ترتيب التغطية هو Arabic Mobile ثم Arabic Desktop ثم English/LTR parity، مع حالات تفاعل محددة حسب قابلية انطباقها، وليس نسخ كل حالة على كل عنصر بلا معنى.

## 2. الهدف والنتيجة المتوقعة

عند اكتمال HDL-02 يوجد في ملف Figma المشترك:

1. فهرس واضح وصفحات/Sections مهيأة لـFoundations وComponents وFlows وPresets وQA.
2. Foundations مكتملة للون، Typography العربية، المسافات، الحواف، الشبكات، الارتفاع/الظل، الأيقونات، وأسلوب الصور، مع عقود أولية للحركة يحسم HDL-06 قيمها النهائية.
3. Component sets ممثلة وقابلة لإعادة الاستخدام لعائلات المكونات المحددة في §3، وليست رسومات منفصلة.
4. Node ID Registry وSettings Matrix وقالب QA قابلان للاستخدام في كل مواصفة مرئية لاحقة.
5. دورة Revision واعتماد موثقة تمنع الانتقال إلى Plan أو Implementation عند غياب الاعتماد أو عند تقادمه.

النجاح هنا يعني أن المواصفات اللاحقة تستطيع إضافة شاشاتها إلى النظام نفسه وتوريث القواعد المشتركة دون إعادة تعريف الحوكمة أو اختراع Variant غير قابل للتنفيذ.

## 3. النطاق والتصنيف قبل البناء

### فحص الموجود وتصنيفه

يعتمد التصنيف على تقرير HDL-01 المقبول عند SHA المسجل فيه؛ إذا تغيّر المصدر قبل تصميم عنصر يعتمد عليه، يعاد فحص ذلك العنصر ولا تُعامل أرقام التقرير القديمة كدليل حالي.

| التصنيف | ما يخص HDL-02 |
|---|---|
| **Existing — Audit & Polish** | إعدادات الثيم الحالية الـ37 القابلة للتفاعل، والقوالب والمكونات الحالية مثل Header وProduct Card وCart Drawer؛ تُراجع كمصادر حقيقة للـSettings Matrix ولا يُعاد بناؤها داخل HDL-02. |
| **Build** | حوكمة ملف Figma، Foundations، Component sets الممثلة، Node ID Registry، Settings Matrix، وقالب الاعتماد/QA. |
| **Spike** | أي سلوك أو حقل أو Variant لا يثبت من `twilight.json` أو عقد مكوّن قائم أو API موثق أو معاينة سلة حية. |
| **Deferred** | الشاشات والتدفقات الكاملة، تطبيق الكود، نظام الحركة النهائي، هندسة الإعدادات النهائية، والـPresets الأربعة؛ تملكها المواصفات اللاحقة المبينة في §12. |

### داخل النطاق

- إنشاء هيكل Figma وفهرسه بحيث توجد وجهات واضحة لـFoundations وShared Components وFlows وPresets وQA؛ يكفي في Flows وPresets الفهرس وقواعد الإيداع والملكية، ولا يلزم محتوى صفحات كامل في HDL-02.
- تعريف Foundations المذكورة في §2 مع أسماء ثابتة واستعمال موضح وقيود عربية/Responsive.
- إنشاء Component set ممثل واحد على الأقل لكل عائلة: Buttons، Form controls (Input/Select)، Badges/Status، Product price، Product-card skeleton، Drawer/Modal shell، Header/Navigation primitives، Tabs/Accordion، وFeedback states (Loading/Empty/Error).
- توثيق الحالات والتفاعل والتعريب والاتجاه لكل عائلة حسب مصفوفة §8.
- إنشاء Node ID Registry وSettings Matrix وتطبيقهما على جميع مخرجات HDL-02 المعتمدة.
- تعريف دورة Draft → Review → Approved → Superseded/Reopened، وقاعدة تسليمها للمواصفات اللاحقة.

### خارج النطاق

- تصميم Home أو Product أو Collection أو Search أو Cart أو Supporting pages كتدفقات مكتملة.
- تصميم أو اعتماد أي من Presets الأربعة أو متاجر الديمو.
- استبدال مكونات الثيم الموجودة، كتابة Twig/SCSS/JS، أو تعديل `twilight.json`.
- تصميم لوحة تحكم جديدة لسلة؛ نوثق الحقول المؤكدة فقط في Settings Matrix.
- حسم مستويات الحركة الثلاثة أو ميزانية الأداء النهائية؛ يملكهما HDL-06 وHDL-05.
- نسخ كود أو أصول أو نصوص أو هوية Kalles أو Theme Raed، أو استخدام أرقام social proof وهمية كبيانات إنتاج.

أي توسع خارج هذا الحد ينتقل إلى المواصفة المالكة أو `docs/spec-kit/FUTURE-BACKLOG.md`، ولا يدخل HDL-02 بتعديل صامت.

## 4. قصص المستخدم واختبارات القبول المستقلة

### User Story 1 — المالك يعتمد Revision معلومًا (P1)

**بصياغة بسيطة:** كمالك غير تقني أريد أن أرى الشكل والحالات والإعدادات المرتبطة به قبل البرمجة، حتى أعرف بالضبط ما الذي أعتمده.

**اختبار قبول مستقل:**

1. **Given** مخرج HDL-02 حالته `Ready for Owner Review` وله Revision وسجلات Node مكتملة،
2. **When** يفتح المالك روابط العقد من `design.md` ويراجع Arabic Mobile وArabic Desktop وEnglish/LTR والحالات المنطبقة،
3. **Then** يستطيع اعتماد Revision واحد بعبارة **Approved for Implementation** مع اسمه وتاريخه، أو إعادته إلى Draft بملاحظات؛ ولا تتحول أي شاشة بلا هذه البيانات إلى Approved.

### User Story 2 — المصمم يعيد استخدام النظام (P1)

**بصياغة بسيطة:** كمصمم أريد Foundations وComponent sets مشتركة، حتى أبني الشاشات اللاحقة من أصول واحدة بدل إعادة رسم العنصر.

**اختبار قبول مستقل:**

1. **Given** العائلات التسع داخل نطاق HDL-02،
2. **When** يراجع المصمم كل عائلة في Figma،
3. **Then** يجد Component set مسمى، وخصائص/Variants موثقة، والحالات المنطبقة، ومراجع Foundation المستخدمة؛ ولا تكون النسخ المطلوبة رسومات Detached مستقلة.

### User Story 3 — المطور يتتبع التصميم إلى قدرة حقيقية (P1)

**بصياغة بسيطة:** كمطور أريد Node IDs ومصدر كل Variant، حتى لا أخمن الشكل أو السلوك أو وجود إعداد في سلة.

**اختبار قبول مستقل:**

1. **Given** عينة من ثلاثة Variants قابلة للاختيار من ثلاث عائلات مختلفة،
2. **When** يتبع المطور سجل Node ثم صف Settings Matrix لكل Variant،
3. **Then** يصل لكل واحد إلى Setting ID/Component field/عقد منصة مؤكد، أو يجد علامة `Spike` ومالك الحسم؛ ويكون عدد Variants غير المثبتة وغير الموسومة صفرًا.

### User Story 4 — مواصفة لاحقة تستلم الأساس (P2)

**بصياغة بسيطة:** كمالك لمواصفة مرئية لاحقة أريد قالب تسليم موحدًا، حتى أعرف ما يجب تصميمه واعتماده قبل Plan.

**اختبار قبول مستقل:**

1. **Given** مواصفة مرئية لاحقة مثل HDL-07 أو HDL-09،
2. **When** تنشئ سجلها في النظام،
3. **Then** تستخدم اسمًا يبدأ بمعرفها، وتسجل Node IDs وRevision والتغطية وSettings Matrix في `design.md`، ولا تنتقل إلى Plan حتى تكون الحالة Approved للـRevision الحالي.

## 5. المتطلبات الوظيفية

- **HDL-02-FR-001 — design.md وسجل Node IDs:** يكون لكل مواصفة مرئية `design.md` يذكر رابط ملف Figma والصفحة وRevision وحالة الاعتماد. يحتوي Node ID Registry سجلًا فريدًا لكل Frame أو Component set معتمد: `spec_id`، الاسم القانوني، النوع، Figma Page/Section، Node ID والرابط المباشر، الجهاز، اللغة/الاتجاه، الحالات المغطاة، Revision، الحالة، المالك، تاريخ الاعتماد، و`supersedes` إن وجد. إعادة إنشاء/نقل عقدة تتطلب تحديث السجل؛ لا يجوز أن يشير سجل Approved إلى Node محذوف أو Revision آخر.
- **HDL-02-FR-002 — ترتيب اللغة والجهاز:** يبدأ التصميم بـArabic Mobile، ثم Arabic Desktop، ثم English/LTR parity. تشمل parity كل عائلة نصية أو اتجاهية أو تفاعلية، وتتحقق من طول النص، اتجاه الأيقونات، المحاذاة، ترتيب التركيز، وفتح Drawer/Modal؛ لا يعتمد أي تفاعل على Hover وحده.
- **HDL-02-FR-003 — السلوك والحالات:** لا تكفي لقطة ثابتة لعنصر تفاعلي. يوثق العنصر تسلسل الفتح/الإغلاق أو الضغط/الاستجابة وحالات Default وHover وFocus-visible وPressed وDisabled حيث تنطبق، إضافة إلى Loading/Empty/Error للعناصر المعتمدة على بيانات، وSold out لعناصر التجارة. الحالات غير المنطبقة تسجل `N/A` مع السبب بدل رسم حالة مصطنعة.
- **HDL-02-FR-004 — إثبات قابلية الـVariants:** كل Variant ظاهر كتفضيل للتاجر أو كتغيير سلوكي يحمل Evidence Reference إلى واحد من: Setting ID موجود في `twilight.json`، Component field/عقد قائم، API موثق من Salla/Twilight، أو Spike مثبت على متجر سلة حي. غير المؤكد يوسم `Spike — Not approved for implementation` مع مواصفة مالكة ومعيار حسم، ولا يدخل قائمة الخيارات القابلة للتنفيذ حتى يحسم.
- **HDL-02-FR-005 — Settings Matrix:** تحتوي المصفوفة صفًا لكل خاصية مرئية متغيرة: المكوّن/العقدة، الخاصية، المواصفة المالكة، النطاق (`Global` أو `Component` أو `Fixed`)، مستوى الظهور (`Basic` أو `Advanced` أو `Not merchant-controlled`)، Setting ID أو Component field، القيم والقيمة الافتراضية، اختلاف Mobile إن وجد، حالة الإثبات (`Confirmed` أو `Spike`)، ومرجع الدليل. `Global` يؤثر في المتجر كله، و`Component` لا يتجاوز حقول القسم، و`Fixed` قرار جودة لا يظهر للتاجر. لا تنشئ HDL-02 إعدادات جديدة ولا تستخدم Setting ID مقترحًا كحقيقة.
- **HDL-02-FR-006 — التسمية القانونية:** تستخدم أسماء ثابتة تبدأ بمعرف المواصفة وبالبنية `HDL-XX/Component/Viewport/Direction/State`، مثل `HDL-09/SearchDrawer/Mobile/RTL/Loading`. اسم Foundation أو Component set المشترك يبدأ `HDL-02/Shared/…`، ويحظر اسمان مختلفان للكيان نفسه داخل السجل.
- **HDL-02-FR-007 — دورة الاعتماد والRevision:** الحالات القانونية هي `Draft` ثم `Ready for Owner Review` ثم `Approved`، وبعد التغيير `Superseded` أو `Reopened`. وحده المالك يضع **Approved for Implementation** مع الاسم والتاريخ ورقم Revision داخل `design.md`. أي تغيير بعد الاعتماد يمس الشكل المرئي أو السلوك أو الاستجابة أو النص/الاتجاه أو Variant/إعداد التاجر يرفع Revision، يجعل الاعتماد السابق Superseded، ويمنع Plan/Implementation حتى إعادة المراجعة. تصحيح وصف أو رابط لا يغير النية يجوز داخل Revision نفسه مع سجل تعديل.
- **HDL-02-FR-008 — سجل الفروقات:** بعد تنفيذ أي مواصفة لاحقة، تسجل المقارنة بين Node المعتمد ومعاينة سلة بعد آخر Build: الفرق، وتصنيفه (`Bug` أو `Salla Platform` أو `Responsive` أو `Accessibility` أو `Performance` أو `Product Decision`)، والدليل اللاحق للتغيير، والقرار، وموافقة المالك عند قبول الفرق. لا يعد Mockup محلي دليلًا عن الثيم.
- **HDL-02-FR-009 — المخرج المحدود القابل للتسليم:** تكتمل HDL-02 بهيكل الملف، Foundations، العائلات التسع الممثلة، Node Registry، Settings Matrix، وقالب QA/approval فقط. الصفحات والتدفقات والـPresets الكاملة لا تعد نقصًا في HDL-02 إذا كانت وجهاتها ومالكوها مسجلين للتسليم اللاحق.
- **HDL-02-FR-010 — بوابة المواصفات اللاحقة:** كل مواصفة مرئية لاحقة ترث Foundations والحوكمة، وتضيف Frames/Components المملوكة لها إلى سجل Node وإلى `design.md` الخاص بها. لا تبدأ Plan أو Tasks أو تنفيذ واجهة للـRevision الحالي قبل اكتمال السجل والتغطية والموافقة؛ الاستثناء الوحيد قرار مالك موثق بالنطاق والسبب وتاريخ الانتهاء وخطة الإزالة.

## 6. نموذج المعلومات وقواعد الهوية

| الكيان | هويته وقواعده |
|---|---|
| **Foundation token/style** | اسم قانوني فريد يبدأ `HDL-02/Shared`; يوضح الغرض لا اسمًا زخرفيًا، ويذكر قيود RTL/Arabic والاستخدام. |
| **Component set** | عائلة وظيفية واحدة؛ الاختلاف الشكلي Variant، والاختلاف الجوهري في البيانات/السلوك يبرر Component منفصلًا. |
| **Design revision** | رقم متزايد داخل المواصفة؛ Approval يرتبط به وحده ولا ينتقل تلقائيًا إلى Revision أحدث. |
| **Node registry record** | المفتاح المركب `spec_id + canonical_name + revision`; Node ID والرابط يجب أن يحلا إلى العقدة نفسها في ملف Figma المسجل. |
| **Settings Matrix row** | خاصية مرئية واحدة ومالك واحد ومصدر تحكم واحد؛ لا يستخدم Setting ID لمعنيين. |
| **Approval record** | عبارة الاعتماد + اسم المالك + التاريخ + Revision؛ غياب أي حقل يجعل الحالة Pending. |
| **Deviation record** | Node/Revision معتمد + دليل معاينة سلة + سبب مصنف + قرار ومالك؛ لا يمحو التصميم الأصلي. |

عند تعديل متزامن، آخر Revision معتمد هو المرجع الوحيد للتنفيذ؛ لا تدمج موافقتين جزئيتين من Revisionين. يعاد التعديل المتعارض إلى `Reopened` حتى يصدر Revision موحد.

## 7. إعدادات التاجر المتوقعة

لا تضيف HDL-02 إعداد تاجر جديدًا. تستخدم الـSettings Matrix الإعدادات والحقول المؤكدة كأدلة، وتسلّم أي حاجة جديدة إلى HDL-03 أو المواصفة المالكة كـSpike.

قواعد العرض التي يجب أن يعكسها التصميم:

- الخيارات الأساسية مفهومة أولًا، والتفاصيل الدقيقة `Advanced` عندما تسمح سلة.
- `Global` للقرار الذي يؤثر في المتجر كله؛ `Component` لمحتوى أو تخطيط قسم واحد.
- `Follow Preset` هو الاتجاه الافتراضي لاحقًا مع Override يدوي فقط عند حاجة حقيقية؛ HDL-03 يثبت العقد النهائي.
- كل Setting ID له معنى واحد وقيمة افتراضية آمنة، ولا يضاف خيار لزيادة العدد.

## 8. مصفوفة تغطية الاتجاه والحالات

| التغطية | المطلوب للقبول |
|---|---|
| Arabic Mobile | Default لكل العائلات التسع، مع النص الطويل والبيانات الناقصة حيث تنطبق؛ هي نقطة البداية. |
| Arabic Desktop | Responsive layout لكل العائلات، وHover للعناصر ذات مؤشر، من دون جعل Hover شرطًا للوصول للوظيفة. |
| English/LTR | Parity لكل عنصر نصي أو اتجاهي أو تفاعلي؛ تشمل اتجاه الأيقونة، ترتيب المحتوى، فتح الـOverlay، والتركيز. |
| Keyboard/Focus | Focus-visible وتسلسل منطقي لكل عنصر تفاعلي؛ لا يقبل عنصر بلا حالة تركيز واضحة. |
| Async/Data | Loading وEmpty وError لأي عائلة تنتظر بيانات أو تعرض مجموعة؛ `N/A` مسبب للبقية. |
| Commerce | Disabled وSold out عند السعر/البطاقة/الإجراء التجاري، مع بقاء السعر والتوفر والإجراء واضحًا. |
| Motion | وصف الانتقال وبديل `prefers-reduced-motion` للعناصر المتحركة؛ القيم النهائية ومستويات الحركة يملكها HDL-06. |

يجب ألا يمنع اللون وحده فهم الحالة، ويجب أن تراعي Annotation التباين، حجم هدف اللمس، تكبير النص، عدم قص النص العربي، وترتيب القراءة. القياس النهائي للوصول والأداء يتم على معاينة سلة في المواصفة التي تنفذ المكوّن، لا داخل رسم Figma وحده.

## 9. الحالات الطرفية وحالات الفشل

- Variant جميل لكنه لا يملك مصدر تحكم مؤكد: يتحول إلى Spike ولا يُعتمد للتنفيذ.
- Node معتمد حُذف أو تغير رابطه: تصبح حالته Reopened حتى تحديث السجل وإعادة التحقق.
- تعديل بعد الاعتماد: يبقى Revision السابق تاريخيًا Superseded ولا يستمر اعتماده على الجديد.
- النص العربي أو الإنجليزي يتجاوز المساحة: يختبر الالتفاف/الاقتطاع المقصود ولا يصغر الخط تحت حدود القراءة لمجرد احتواء النص.
- وظيفة تظهر على Hover فقط: يضاف مسار لمس ولوحة مفاتيح قبل الاعتماد.
- State غير منطقية لعائلة معينة: تسجل `N/A` مع السبب، ولا تنسخ حالات زائفة لإكمال جدول شكلي.
- تضارب Sticky element أو Drawer مع مساحة الجوال: يسجل كحالة تنسيق تملكها المواصفة اللاحقة، ولا يحسم برسم منفصل داخل HDL-02.
- اختلاف Figma عن سلة بسبب منصة أو وصول أو أداء: يسجل وفق FR-008 ولا يسمى مقبولًا قبل موافقة المالك.
- مصدر HDL-01 صار أقدم من تعديل المستودع: يعاد فحص الإعداد أو المكوّن المتأثر قبل الاستشهاد به.

## 10. بوابة Figma قبل Plan أو التنفيذ

**نوع البوابة:** نظام تصميم وحوكمة مرئية، لا تصميم جميع صفحات المنتج.

لا تنتقل HDL-02 إلى Plan قبل تحقق جميع البنود:

- [x] رابط ملف Figma والصفحة/Section الحالية ورقم Revision مسجلة في `design.md`.
- [x] Foundations ضمن النطاق مكتملة ومسمّاة ومشروحة.
- [x] العائلات التسع موجودة كـComponent sets قابلة لإعادة الاستخدام.
- [x] Node ID Registry مكتمل لكل مخرج مطلوب في هذا Revision، وكل رابط يحل إلى عقدته.
- [x] Settings Matrix تغطي 100% من الخصائص القابلة للاختيار في مخرجات HDL-02.
- [x] لا Variant قابل للتنفيذ بلا دليل Confirmed، ولا Unknown بلا علامة Spike ومالك حسم.
- [x] مصفوفة §8 مكتملة أو تحمل `N/A` مسببًا لكل حالة غير منطبقة.
- [x] الحالات التفاعلية موضحة بتسلسل/Prototype أو Annotation قابل للاختبار، لا بلقطة Default فقط.
- [x] المالك اعتمد التنفيذ بالعبارة المعرفة لهذه البوابة `APPROVE HDL-02 REV 2`، مع اسمه وتاريخه وRevision داخل `design.md`.

وتصبح البوابة Pending تلقائيًا إذا تغير Node معتمد أو Revision أو سلوك/Variant بعد الموافقة.

## 11. الأدلة المطلوبة للقبول ومعايير النجاح

### أدلة قبول HDL-02

- [x] لا توجد علامات توضيح غير محسومة أو عناصر نائبة أو أسئلة منتج مفتوحة في هذه المواصفة.
- [x] 100% من فئات Foundations المذكورة في §2 لها Style/Variable أو قاعدة موثقة ومالك تسليم لاحق حيث يلزم.
- [x] 9/9 عائلات ممثلة بـComponent set موثق، وليس برسومات منفصلة فقط.
- [x] 100% من العقد المعتمدة لها سجل Node كامل، وصفر روابط مكسورة عند المراجعة.
- [x] 100% من Variants القابلة للاختيار `Confirmed` بمصدر أو `Spike — Not approved for implementation`; العدد غير المصنف = 0.
- [x] 100% من صفوف تغطية §8 مكتملة أو `N/A` مع سبب.
- [x] Revision الحالي يحمل موافقة المالك الكاملة، ولا توجد موافقة من Revision أقدم مستخدمة كحالية.
- [x] لا أصل أو نص أو هوية من Kalles أو Theme Raed، ولا social proof وهمي مقدم كبيانات إنتاج.

### بوابات الكود والمعاينة

HDL-02 مخرج تصميم/حوكمة ولا يغير `src/` أو `public/`؛ لذلك يسجل Production build وtheme guard ومعاينة سلة كـ`N/A — no source change` بدل ادعاء تحقق بصري للثيم. إذا أدخل Plan لاحقًا أي تغيير مصدر ضمن هذه المواصفة، تصبح البنود التالية إلزامية ولا يجوز إبقاؤها `N/A`:

- `npx webpack --mode production` ينجح.
- `node scripts/check-theme.mjs --build` ينجح بلا أخطاء جديدة.
- معاينة سلة الحقيقية بعد آخر تعديل، مع Mobile/Desktop وArabic RTL وEnglish LTR حيث ينطبق.
- أثر الحجم والشبكة والأداء والوصول مقاس، وأي انحدار مادي مرفوض أو مستثنى بقرار مالك وخطة علاج.

كل مواصفة مرئية لاحقة يجب أن تكرر هذه البوابات بعد تنفيذها؛ Figma تثبت النية ولا تثبت سلوك الثيم المصيّر.

## 13. الافتراضات والقرارات المؤجلة صراحة

- مصدر Figma الحالي ورابطه يسجلان في `design.md`; Node IDs النهائية **مخرج من مرحلة التصميم** وليست سؤال منتج متبقيًا من Clarify.
- تقرير HDL-01 هو خط الأساس المقبول للموجود، لكنه صالح فقط للـSHA المسجل؛ التعديلات اللاحقة تتطلب إعادة فحص الجزء المتأثر.
- أي قدرة سلة غير مؤكدة لا تحسم بالتخمين في هذه المواصفة؛ تنتقل كـSpike بمالك ومعيار حسم.
- لا فروقات مقبولة مسبقًا بين Figma ومعاينة سلة؛ تسجل الفروقات الفعلية بعد التنفيذ ويقرر المالك كل واحدة.
- تفاصيل بنية ملفات الكود، الأدوات، والميزانيات الرقمية النهائية موضوع Plan أو المواصفات المالكة، وليست قرارًا مطلوبًا لإكمال Clarify.

## 14. تعريف الانتهاء

تعتبر HDL-02 منتهية فقط عندما:

1. تغطي مخرجات Figma المتطلبات `HDL-02-FR-001` إلى `HDL-02-FR-010` ضمن الحد المحدد، من دون اشتراط تصميم كل صفحات المشروع.
2. تكون Foundations والعائلات التسع وNode Registry وSettings Matrix وقالب QA قابلة لإعادة الاستخدام ومكتملة القياس حسب §11.
3. لا يوجد Variant غير مثبت وغير موسوم، ولا سؤال منتج جوهري مفتوح.
4. يحمل Revision الحالي موافقة ياسر، وتكون دورة التعديل/إلغاء الاعتماد قابلة للتطبيق.
5. تسجل بوابات الكود والمعاينة بصدق: ناجحة إذا وُجد تغيير مصدر، أو `N/A — no source change` إذا بقي المخرج تصميميًا فقط.
